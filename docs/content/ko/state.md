# 상태를 둘 곳 고르기

Worker는 요청마다 깨끗한 방을 받으므로 상태는 항상 밖에 둡니다. 문제는 어디에 두느냐이고, **일관성·크기·과금** 세 가지가 답을 정합니다.

## 일관성에서 출발

| 저장소             | 일관성                         | 어울리는 것                |
| ------------------ | ------------------------------ | -------------------------- |
| KV                 | 최종 일관성(최대 60초)         | 설정, 캐시, 플래그         |
| D1                 | 단일 프라이머리, 읽기는 복제본 | 표 형식 데이터, 검색, 집계 |
| R2                 | 객체 단위 강한 일관성          | 파일, 이미지, 백업         |
| Durable Objects    | 한 인스턴스 안에서 직렬화      | 카운터, 재고, 조정, 채팅   |
| Queues / Workflows | 최소 한 번                     | 미뤄 둔 작업, 장기 작업    |

"정확히 하나"를 지켜야 한다면 Durable Objects나 D1 트랜잭션입니다. KV에 카운터를 두면 동시 쓰기에서 값을 잃습니다.

## 크기와 비용으로 좁히기

- KV 값은 25MB까지, 쓰기가 읽기보다 비쌈(100만 쓰기당 $5)
- D1은 **읽은 행 수**와 **쓴 행 수**로 과금. 인덱스 없는 `WHERE`는 모든 행에 과금
- R2는 저장량과 작업 수, **전송은 무료**라서 배포에 적합
- DO는 유휴 시 과금되지 않음(hibernation). 요청 수와 GB초

## 안티패턴

- 세션을 KV에 쓰고 바로 읽기 → 반영 전이라 null. 응답에 담아 돌려주기
- 이미지를 D1에 저장 → 행이 커지고 읽기 비용 폭증. 바이트는 R2, 키만 D1
- 모든 것을 하나의 DO에 → 호출이 직렬화되어 막힘. 핫스팟만
- 전역 변수 캐시 → isolate가 바뀌면 사라짐. 잃어도 되는 것만

## 자주 쓰는 조합

1. **R2 + D1**: 파일은 R2, 메타데이터는 D1. 목록은 D1, 조회는 R2
2. **KV + 서명 URL**: 설정은 KV, 배포는 R2 서명 URL로 Worker를 거치지 않음
3. **DO + Queues**: 순서는 DO, 무거운 일은 큐로
4. **Workflows + D1**: 진행 상황을 D1에 쓰고 실패한 step부터 재개

## 이 사이트의 구현

`env.DB`와 `env.COUNTER`는 실제 바인딩을 샌드박스에 그대로 넘깁니다. KV / R2 / AI의 namespace는 isolate로 복제할 수 없어 Durable Object의 RPC로 중계합니다. 어느 경로든 원칙은 같습니다. 상태는 밖에.
