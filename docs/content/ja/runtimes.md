# ランタイム構造の比較（Node.js と V8 isolate）

サーバーサイド JavaScript の歴史は、長らく Node.js のアーキテクチャと同一視されてきた。しかしエッジコンピューティングの要求する「極小の起動時間」「極めて高い収容密度」「安全なマルチテナント分離」の前に、Node.js の前提構造は大きな足枷となる。

Cloudflare Workers を支える **V8 isolate** が何を削ぎ落とし、何を残したのかを理解することで、エッジにおける正確な設計判断が可能になる。

## プロセスモデルと分離アーキテクチャの根本差

Node.js は、1 つの OS プロセスに対して 1 つの V8 インスタンスを割り当てる。その外側には libuv のイベントループ、マルチスレッドプール、ファイルディスクリプタテーブル、そして raw ソケットの管理機構が張り巡らされている。この構造は 1 つのプロセスを永続的に常駐させることを前提としており、リクエストごとにプロセスを新設・破棄する運用には到底耐えられない。

```
[Node.js のプロセス構造]
OS プロセス ── libuv (C++ / スレッドプール / ファイル I/O / ネットワークソケット)
             └── 単一の V8 インスタンス (全リクエストでヒープ・状態を共有)

[Workers の isolate 構造]
単一のホストプロセス ── 分離境界 (メモリ保護・権限サンドボックス)
                      ├── isolate A (ユーザー A のヒープ / 独立メモリ空間)
                      ├── isolate B (ユーザー B のヒープ / 独立メモリ空間)
                      └── isolate C (ユーザー C のヒープ / 独立メモリ空間)
```

Cloudflare Workers は、OS プロセスのレイヤーを完全に隠蔽し、**V8 isolate 単体**を実行の基本単位として扱う。ホストマシンの単一プロセス内に、メモリ空間が厳密に切り離された数千個の isolate を隙間なく詰め込む。

ファイルシステムへのアクセスやソケットの直接制御といった特権的なシステムコールをあらかじめ剥奪しておくことで、他者のコードが同一ホスト内の隣接するメモリ領域を覗き見るリスクを根本から排除している。

## コールドスタートの物理的限界

コンテナ（Docker 等）の起動には、コンテナイメージのレイヤー展開、Linux 名前空間（Namespace）の初期化、仮想ネットワークインターフェースの構成、そしてゲストプロセスの起動という一連のステップが不可欠であり、どれほど最適化しても数百ミリ秒から数秒の時間を要する。

これに対し、isolate の起動は「V8 ヒープ領域の初期化」と「事前コンパイルされたバイトコードのロード」だけで完了する。ネットワークや仮想マシンのブートシーケンスが存在しないため、物理的な制約として 1 〜 5 ミリ秒以内でリクエストの処理を開始できる。

## アーキテクチャの選定境界

| 処理の性質 | 最適な選択肢 | 根拠 |
| --- | --- | --- |
| Web API、軽量ビジネスロジック、データ中継 | **V8 isolate（Workers）** | 起動がミリ秒単位で、アイドルコストがゼロ |
| 長時間動作するバッチ、FFmpeg、Playwright | **Cloudflare Containers** | 完全な Linux カーネルとバイナリ実行環境が不可欠 |
| 外部との接続待ち（DB クエリ、外部 REST API） | **V8 isolate（Workers）** | CPU 時間課金のため、ネットワーク待機時間は無料 |
| 単一リソースへの直列化と排他制御 | **Durable Objects** | 世界で 1 つのインスタンスへリクエストを集約 |

Node.js 向けのライブラリを持ち込む際は `nodejs_compat` 互換フラグを利用できるが、これによって提供されるのは `Buffer`、`crypto`、`events` など Web 標準に近い一部の抽象層に限られる。`fs` によるローカルディスク操作を前提とした設計は、isolate の思想とは根本的に相容れない。
