# エッジにおける状態設計（ストレージの選択基準）

Cloudflare Workers はリクエストごとに独立したメモリ空間で起動する。メモリに状態を留めることは許されないため、データは必然的に外部のストレージ層へ委譲しなければならない。

問題は「どのストレージを選ぶか」である。この選択を誤ると、直前の書き込みが読み取れない幽霊データ現象や、インデックス未設定によるクエリ課金の爆発、単一インスタンスへの過負荷によるボトルネックを招く。選択の判断軸は、**一貫性モデル・データサイズ・課金トリガー** の 3 点に集約される。

## 一貫性モデルによる第一選別

| ストレージ | 一貫性レベル | 最適なユースケース | 危険な誤用 |
| --- | --- | --- | --- |
| **Workers KV** | 結果整合性（最大 60 秒の伝播遅延） | 設定値、機能フラグ、URL リダイレクト表 | 厳密なカウンタ、残高、購入直後のセッション |
| **D1** | プライマリ書き込み、レプリカ読み取り | 構造化データ、リレーション検索、集計 | 数メガバイトを超えるバイナリの格納 |
| **Cloudflare R2** | 強整合性（オブジェクト単位） | 画像、動画、ログ、バックアップ | 数キロバイトの細粒度な頻繁更新 |
| **Durable Objects** | 単一ノードで完全直列化（強い一貫性） | チャットルーム、チケット在庫、分散ロック | 全リクエストの無差別な集約 |
| **Hyperdrive** | 既存リレーショナル DB への接続プール | PostgreSQL / MySQL との高速通信 | - |

「世界で唯一つの最新の値を競合なしに更新したい」場合は Durable Objects を、リレーションや集計が必要な場合は D1 を選ぶ。安易に KV へカウンタを置けば、別々のエッジからの同時書き込みで確実に値の先祖返りが発生する。

## サイズ制約と課金構造の落とし穴

- **Workers KV**: 1 キーあたり 25MB。読み取りコストは極小だが、書き込み単価（100 万回あたり 5 ドル）が相対的に高いため、更新頻度の高い設計は避ける。
- **D1**: 発行クエリ数ではなく**走査した行数**で課金される。`CREATE INDEX` のない `WHERE` クエリは全行をなめて即座に請求を押し上げる。
- **Cloudflare R2**: 保存容量と操作リクエスト数のみが課金対象となり、**下りデータ転送（Egress）が完全無料**である。配信トラフィックが大きい静的ファイルは迷わず R2 へ置く。
- **Durable Objects**: リクエスト数および使用メモリ時間（GB 秒）の従量制。アクセスがない期間は自動ハイバネーションにより課金が停止する。

## 代表的なアンチパターン

1. **セッション保存に KV を採用し、ログイン直後にリダイレクト先で検証する**: 書き込みの伝播遅延により、直後の読み取りでキーが見つからず認証失敗となる。直後の状態遷移は暗号化 Cookie などのステートレスな手段と組み合わせる必要がある。
2. **D1 のカラムに画像や PDF のバイナリを直接格納する**: レコード行のサイズが肥大化し、検索時の読み取り行数課金と I/O 帯域を無駄に浪費する。バイナリ実体は R2 へ逃がし、D1 にはオブジェクトキーのみを記録するのが鉄則である。
3. **全てのトラフィックを 1 つの Durable Object インスタンスへ集中させる**: 直列化機構が裏目に出て、世界中からのリクエストが単一ノードで順番待ちを起こし、レイテンシが急激に悪化する。テナント単位やユーザー単位で ID を細かく分散させなければならない。

## 堅牢な組み合わせパターン

- **R2（実体ファイル）+ D1（メタデータ索引）**: 画像やドキュメントの本体は転送無料の R2 に預け、タグや更新日時、所有者 ID は D1 でインデックス検索する。
- **Durable Objects（整合性の関所）+ Queues（非同期消化）**: 注文の引き当てや在庫の減算は DO で直列化して瞬時に整合性を担保し、重厚な決済処理やメール配信は Queues へ即座に流す。
