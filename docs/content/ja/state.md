# 状態の置き場所を選ぶ

Workers はリクエストごとにまっさらな部屋です。状態は必ず外に置きます。問題は「どれに置くか」で、これは **一貫性・サイズ・課金** の 3 つで決まります。

## 一貫性から決める

| 保存先             | 一貫性                                   | 向くもの                       |
| ------------------ | ---------------------------------------- | ------------------------------ |
| KV                 | 結果整合（最大 60 秒）                   | 設定、キャッシュ、フラグ       |
| D1                 | 単一プライマリ、読みはレプリカ           | 表形式のデータ、検索、集計     |
| R2                 | 読み書きは強い一貫性（オブジェクト単位） | ファイル、画像、バックアップ   |
| Durable Objects    | 1 実体に閉じて直列化                     | カウンタ、在庫、調整、チャット |
| Queues / Workflows | 少なくとも 1 回                          | 後回しの処理、長時間ジョブ     |

「厳密に 1 つ」を守りたいなら Durable Objects か D1 のトランザクションです。KV にカウンタを置くと、同時書き込みで値を失います。

## サイズと課金で絞る

- KV の値は 25MB まで。書き込みは読みより高い（$5 / 100 万書き込み）
- D1 は **読んだ行数** と **書いた行数** で課金。索引のない `WHERE` は全行課金
- R2 は保存量と操作回数。**転送は無料** なので配信はここ
- DO はアイドル中は課金されない（hibernation）。リクエスト数と GB 秒

## アンチパターン

- セッションを KV に置いて「書いた直後に読む」→ 反映前で null になる。直後はレスポンスで返す
- D1 に画像を入れる → 行が太り、読み取り課金が跳ねる。R2 に置いてキーだけ持つ
- DO にすべてを集める → 呼び出しが直列化されて詰まる。ホットスポットだけに
- グローバル変数にキャッシュを持つ → isolate が変われば消える。消えても困らないものだけ

## 組み合わせの型

1. **R2 + D1**: ファイルは R2、メタデータは D1。一覧は D1、取得は R2
2. **KV + 署名付き URL**: 設定は KV、配信は R2 の署名付き URL で Worker を通さない
3. **DO + Queues**: DO で順序を守り、重い処理は Queue に逃がす
4. **Workflows + D1**: 途中経過を D1 に書き、失敗しても step から再開

## この教材での実装

`env.DB` と `env.COUNTER` は本物のバインディングをサンドボックスへ直接渡しています。KV / R2 / AI は namespace を isolate に渡せないため、Durable Object の RPC を挟んで中継しています。どの経路も「外に置く」という原則は同じです。
