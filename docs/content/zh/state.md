# 选择状态的存放位置

Worker 每个请求都是一间干净的房间，所以状态必须放在外面。问题在于放哪里，由三件事决定：**一致性、大小、费用**。

## 从一致性出发

| 存储               | 一致性                 | 适合                     |
| ------------------ | ---------------------- | ------------------------ |
| KV                 | 最终一致（最长 60 秒） | 配置、缓存、开关         |
| D1                 | 单主库，读走副本       | 表格数据、搜索、聚合     |
| R2                 | 单个对象强一致         | 文件、图片、备份         |
| Durable Objects    | 单个实例内串行化       | 计数器、库存、协调、聊天 |
| Queues / Workflows | 至少一次               | 延后处理与长任务         |

如果要保证“恰好一个”，用 Durable Objects 或 D1 事务。把计数器放在 KV 里，并发写会丢值。

## 用大小和费用收敛

- KV 单个值 25MB；写入比读取贵（每百万次写入 $5）
- D1 按**读取行数**和**写入行数**计费；没有索引的 `WHERE` 会为每一行付费
- R2 按存储量和操作数计费，**出网免费**，所以用它来分发
- DO 空闲时不计费（hibernation）；按请求数和 GB 秒计费

## 反模式

- 把会话写进 KV 后立刻读 → 还没同步就是 null。直接把它放进响应返回
- 把图片存进 D1 → 行变胖，读费用飙升。字节放 R2，只存 key
- 把所有东西塞进一个 DO → 调用串行化后堵住。只放热点
- 用全局变量做缓存 → isolate 一换就没了。只缓存丢了也无所谓的东西

## 常见的组合

1. **R2 + D1**：文件在 R2，元数据在 D1。列表查 D1，读取走 R2
2. **KV + 签名 URL**：配置放 KV，分发用 R2 的签名 URL，不经过 Worker
3. **DO + Queues**：DO 保证顺序，重活丢给队列
4. **Workflows + D1**：把进度写进 D1，失败后从 step 继续

## 本站的做法

`env.DB` 和 `env.COUNTER` 把真实绑定直接交给沙箱。KV / R2 / AI 的 namespace 不能克隆进 isolate，所以通过 Durable Object 的 RPC 中转。无论哪条路径，原则都一样：状态放在外面。
