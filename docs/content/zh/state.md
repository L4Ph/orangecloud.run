# 边缘端的状态设计（存储选择标准）

Cloudflare Workers 在每次请求时都在独立的内存空间中启动。由于不允许将状态保留在内存中，因此数据必须委托给外部存储层。

问题在于“选择哪种存储”。如果选择错误，会导致前一次写入无法读取的“幽灵数据”现象、因未设置索引而引发的查询费用爆炸，以及单个实例过载导致的瓶颈。选择的判断标准可归纳为 **一致性模型、数据大小、计费触发机制** 这三点。

## 基于一致性模型的初步筛选

| 存储 | 一致性级别 | 最佳用例 | 危险误用 |
| --- | --- | --- | --- |
| **Workers KV** | 结果一致性（最大 60 秒的传播延迟） | 配置值、功能标志、URL 重定向表 | 严格的计数器、余额、购买后的会话 |
| **D1** | 主写入、副本读取 | 结构化数据、关系查询、聚合 | 存储超过数兆字节的二进制数据 |
| **Cloudflare R2** | 强一致性（按对象） | 图片、视频、日志、备份 | 数千字节的细粒度频繁更新 |
| **Durable Objects** | 在单个节点上完全串行化（强一致性） | 聊天室、工单库存、分布式锁 | 对所有请求进行无差别聚合 |
| **Hyperdrive** | 连接池至现有关系型数据库 | 与 PostgreSQL / MySQL 的高速通信 | - |

如果“希望在无竞争的情况下更新全球唯一的最新值”，请选择 Durable Objects；如果需要关系或聚合，请选择 D1。如果随意在 KV 中放置计数器，在来自不同边缘的同时写入时，肯定会发生值的回溯。

## 大小限制与计费结构的陷阱

- **Workers KV**：每个键 25MB。虽然读取成本极低，但写入单价（每 100 万次 5 美元）相对较高，因此应避免采用更新频率高的设计。
- **D1**：计费基于**扫描的行数**而非发出的查询数。没有 `CREATE INDEX` 的 `WHERE` 查询会直接导致所有行被计入，从而立即推高计费额。
- **Cloudflare R2**：仅计费存储容量和操作请求数，且**下行数据传输（Egress）完全免费**。对于传输流量较大的静态文件，请毫不犹豫地将其放入 R2。
- **Durable Objects**：按请求数及使用内存时间（GB 秒）计费。在没有访问的期间，通过自动休眠停止计费。

## 代表性反模式

1. **采用 KV 保存会话，并在登录后立即在重定向目标端进行验证**：由于写入传播延迟，随后的读取时无法找到键，导致认证失败。随后的状态转移需要结合加密 Cookie 等无状态（stateless）手段。
2. **在 D1 的列中直接存储图片或 PDF 的二进制数据**：记录行的大小会膨胀，浪费了检索时的读取行数计费和 I/O 带宽。二进制实体应移至 R2，在 D1 中仅记录对象键是铁律。
3. **将所有流量集中到单个 Durable Object 实例上**：串行化机制反而产生反效果，来自全球的请求在单个节点上排队，导致延迟急剧恶化。必须按租户或用户单位细分 ID。

## 稳健的组合模式

- **R2（实体文件）+ D1（元数据索引）**：将图片或文档的主体存放在免费传输的 R2 中，而将标签、更新日期、所有者 ID 在 D1 中进行索引检索。
- **Durable Objects（一致性关卡）+ Queues（异步处理）**：订单分配或库存扣除在 DO 中串行化以瞬间确保一致性，而繁重的支付处理或邮件分发则立即流向 Queues。
