# Durable Objects (분산 상태 관리)

Workers의 가장 큰 강점은 상태가 없는(stateless) 특성 덕분에 전 세계 에지에서 순식간에 스케일링할 수 있었다는 점이었다. 하지만 실제 애플리케이션은 공동 편집 커서 동기화, 채팅방 참여자 관리, 한정 티켓의 재고 할당 등 '전 세계에서 단 하나뿐이며 절대 모순되어서는 안 되는 상태'를 요구한다.

글로벌 변수에 의존하면 서로 다른 isolate에서 값이 엇갈리고, 일반적인 데이터베이스에서는 동시 쓰기의 락 충돌로 골머리를 앓게 된다. 이러한 딜레마를 해결하기 위해 설계된 것이 **Durable Objects(DO)**이다.

## 단일 엔티티와 직렬화 보장

Durable Objects는 **지정한 ID 또는 이름마다 전 세계에서 항상 단 하나의 인스턴스만 존재한다**는 점을 플랫폼이 보장한다.

1. **유일무이한 위치**: 도쿄에서 접속하든 런던에서 접속하든, 동일한 `name`을 지정하는 한 요청은 지구상 어느 한 곳에 배치된 동일한 인스턴스로 라우팅된다.
2. **메시지 직렬화**: 해당 인스턴스에 대한 메서드 호출이나 HTTP 요청은 큐에 쌓여 **하나씩 순차적으로 직렬화되어 실행된다**. 내부에서 동시에 여러 코드가 병행 실행되지 않으므로, 락이나 트랜잭션 격리 수준을 직접 구현할 필요가 전혀 없다.
3. **휘발성 없는 영속 스토리지**: 인스턴스에는 전용 내장 SQLite 스토리지(`ctx.storage`)가 갖춰져 있어, 메모리상의 변수뿐만 아니라 디스크로의 데이터 저장까지 단일 노드 내에서 완결된다.

## 개발자가 파악해야 할 특성

- 클라이언트 측에서는 바인딩을 통해 RPC(원격 프로시저 호출) 형식으로 직관적으로 메서드를 호출할 수 있다.
- 접속이 끊기면 인스턴스는 자동으로 메모리에서 제거(하이버네이션)되어 불필요한 비용이 발생하지 않는다. 다음 요청이 도착하는 순간 수 밀리초 만에 복구된다.
- `ctx.storage.setAlarm()`을 호출하여 향후 특정 시점에 인스턴스를 자동으로 기동시켜 타이머 처리나 클린업을 실행할 수 있다.

에디터상의 `env.COUNTER`는 실제로 가동 중인 Durable Object 인스턴스이다. 코드를 반복 실행하면 프로세스가 재시작되어도 카운터가 확실하게 계속 증가하는 동작을 확인할 수 있다.
