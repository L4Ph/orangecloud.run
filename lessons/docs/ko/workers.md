# Workers의 실행 모델

기존의 서버 개발 감각으로 Worker를 작성하기 시작하면, 가장 먼저 실망하게 되는 것이 바로 전역 변수의 수명이다. 요청 간에 공유할 수 있는 메모리는 어디에 있을까? 정답은, 어디에도 없다.

Worker의 본질은 **HTTP 요청이 도착할 때마다 호출되는 순수한 함수**에 불과하다. `fetch(request, env, ctx)`가 받은 요청을 처리하고 반환한 `Response` 객체가 그대로 전 세계 클라이언트로 전송된다.

## 지배하는 4가지 제약

1. **상태는 요청을 넘어 존속하지 않는다.** 전역 변수에 적어 넣은 값은 동일한 isolate가 우연히 재사용되는 동안만 살아남는다. 다음 요청이 다른 대륙의 데이터 센터로 날아가면, 그곳에 있는 것은 깨끗한 메모리다. 영속화하고 싶은 데이터는 반드시 KV, D1, R2 또는 Durable Objects로 옮겨야 한다.
2. **파일 시스템도 상주 소켓도 없다.** 디스크에 임시 파일을 쏟아낼 수도, 생소켓(Raw socket)을 열어 대기할 수도 없다. 외부와의 통신 경로는 `fetch()`와 플랫폼이 주입하는 바인딩(`env.DB` 등)으로 한정된다.
3. **과금은 CPU 시간으로 계산된다.** 외부 API의 응답을 기다리는 시간이나 타이머로 정지해 있는 시간은 과금 대상이 되지 않는다. 마이크로서비스의 집약 프로キシ로서 Workers를 매우 저렴하게 운용할 수 있는 이유가 바로 여기에 있다.
4. **하드웨어 제한이 가장 먼저 위협이 된다.** 메모리 상한은 128MB. CPU 실행 시간은 무료 요금제에서 1회당 10ms, 유료 요금제에서도 기본적으로 30초(최대 5분)로 제한된다. 무한 루프를 돌리면 시스템이 해당 isolate를 가차 없이 강제 종료한다.

## 제한치 비교

| 항목       | 무료 플랜 | 유료 플랜            |
| ---------- | ---------- | --------------------- |
| 요청 | 10만/일   | 1,000만/월 + 종량제    |
| CPU 시간   | 10ms/회    | 30초/회(최대 5분) |
| 메모리     | 128MB      | 128MB                 |

"요청마다 마련되는, 일회용의 깨끗한 방". 이 멘탈 모델이 정착되면 서버리스의 함정에 빠지는 일은 없게 된다.

```js
export default {
  async fetch(request, env, ctx) {
    // request: 수신한 HTTP 요청
    // env: 바인딩(KV, D1, 시크릿 등)
    // ctx: waitUntil 등의 라이프사이클 제어
    return new Response('hello from workers');
  },
};
```
