# Workers の実行モデル

従来のサーバー開発の感覚で Worker を書き始めると、真っ先に裏切られるのがグローバル変数の寿命である。リクエスト間で共有できるメモリはどこにあるのか。答えは、どこにもない。

Worker の本質は、**HTTP リクエストが届くたびに呼び出される純粋な関数**にすぎない。`fetch(request, env, ctx)` が受け取ったリクエストを処理し、返した `Response` オブジェクトがそのまま世界中のクライアントへ送り出される。

## 支配する 4 つの制約

1. **状態はリクエストをまたいで存続しない。** グローバル変数に書き込んだ値は、同じ isolate が偶然再利用されている間だけ生き残る。次のリクエストが別の大陸のデータセンターへ飛べば、そこにあるのはまっさらなメモリである。永続化したいデータは、必ず KV、D1、R2、あるいは Durable Objects へ逃がさなければならない。
2. **ファイルシステムも常駐ソケットもない。** ディスクへ一時ファイルを吐き出すことも、Raw ソケットを開いて待ち受けることもできない。外部との通信路は `fetch()` と、プラットフォームが注入するバインディング（`env.DB` 等）に限られる。
3. **課金は CPU 時間で計算される。** 外部 API からのレスポンスを待っている時間や、タイマーで停止している時間は課金対象にならない。マイクロサービスの集約プロキシとして Workers が極めて安価に運用できる理由はここにある。
4. **ハードウェアの制限が真っ先に牙をむく。** メモリ上限は 128MB。CPU 実行時間は無料枠で 1 回あたり 10ms、有料枠でも既定で 30 秒（最大 5 分）に縛られる。無限ループを回せば、システムがその isolate を容赦なく強制終了する。

## 制限値の比較

| 項目       | 無料プラン | 有料プラン            |
| ---------- | ---------- | --------------------- |
| リクエスト | 10 万/日   | 1,000 万/月 + 従量    |
| CPU 時間   | 10ms/回    | 30 秒/回（最大 5 分） |
| メモリ     | 128MB      | 128MB                 |

「リクエストごとに用意される、使い捨ての清潔な部屋」。このメンタルモデルが定着すれば、サーバーレスの罠に落ちることはなくなる。

```js
export default {
  async fetch(request, env, ctx) {
    // request: 受信した HTTP 要求
    // env: バインディング（KV、D1、シークレット等）
    // ctx: waitUntil 等のライフサイクル制御
    return new Response("hello from workers");
  },
};
```
