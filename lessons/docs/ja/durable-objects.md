# Durable Objects（分散状態管理）

Workers の最大の強みは、状態を持たない（ステートレスである）がゆえに世界中のエッジで瞬時にスケールすることだった。しかし現実のアプリケーションは、共同編集のカーソル同期、チャットルームの参加者管理、限定チケットの在庫引き当てなど、「世界でただ一つ、絶対に矛盾してはならない状態」を要求してくる。

グローバル変数に頼れば別々の isolate で値が食い違い、通常のデータベースでは同時書き込みのロック競合に頭を抱える。このジレンマを解くために設計されたのが **Durable Objects（DO）** である。

## 単一実体と直列化の保証

Durable Objects は、**指定した ID または名前ごとに、世界中で常にただ 1 つのインスタンスだけが存在する**ことをプラットフォームが保証する。

1. **唯一無二の所在地**: 東京からアクセスしてもロンドンからアクセスしても、同じ `name` を指定する限り、リクエストは地球上のどこか 1 箇所に配置された同一のインスタンスへとルーティングされる。
2. **メッセージの直列化**: そのインスタンスに対するメソッド呼び出しや HTTP リクエストは、キューに積まれ、**1 つずつ順番に直列化して実行される**。内部で同時に複数のコードが並行して走らないため、ロックやトランザクションの分離レベルを自前で実装する必要が一切ない。
3. **揮発しない永続ストレージ**: インスタンスには専用の組み込み SQLite ストレージ（`ctx.storage`）が備わっており、メモリ上の変数だけでなくディスクへのデータ保存も単一ノード内で完結する。

## 開発者が把握すべき特性

- クライアント側からは、バインディングを通じて RPC（リモートプロシージャコール）形式で直感的にメソッドを呼び出せる。
- アクセスが途絶えるとインスタンスは自動的にメモリから退避（ハイバネーション）され、無駄な課金が発生しない。次のリクエストが届いた瞬間に数ミリ秒で復元される。
- `ctx.storage.setAlarm()` を呼ぶことで、将来の特定時刻にインスタンスを自動起動してタイマー処理やクリーンアップを実行させることができる。

エディタ上の `env.COUNTER` は、実際に稼働している Durable Object インスタンスである。コードを繰り返し実行すると、プロセスが再起動してもカウンタが確実に加算され続ける挙動を確認できる。
