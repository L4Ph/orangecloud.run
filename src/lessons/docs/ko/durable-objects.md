# Durable Objects (분산 상태 관리)

Workers의 강점은 상태가 없는(stateless) 특성 덕분에 전 세계 에지에서 빠르게 스케일링할 수 있다는 점이었다. 하지만 실제 애플리케이션은 공동 편집 커서 동기화, 채팅방 참여자 관리, 한정 티켓의 재고 할당 등 '전 세계에서 단 하나뿐이며 절대 모순되어서는 안 되는 상태'를 요구한다.

글로벌 변수에 의존하면 서로 다른 isolate에서 값이 엇갈리고, 일반적인 데이터베이스에서는 동시 쓰기의 락 충돌로 골머리를 앓게 된다. 이러한 딜레마를 해결하기 위해 설계된 것이 **Durable Objects(DO)**이다.

## 단일 엔티티와 직렬화 보장

Durable Objects는 **지정한 ID 또는 이름마다 전 세계에서 동시에 실행되는 인스턴스가 단 하나뿐**이라는 점을 플랫폼이 보장한다. 이 유일성은 새 이벤트가 시작될 때와 스토리지에 접근할 때 확인된다.

1. **유일무이한 위치**: 도쿄에서 접속하든 런던에서 접속하든, 동일한 `name`을 지정하는 한 요청은 지구상 어느 한 곳에 배치된 동일한 인스턴스로 라우팅된다.
2. **메시지 직렬화**: 인스턴스는 단일 스레드로 동작하므로, 메서드 호출이나 HTTP 요청의 JavaScript가 동시에 실행되는 일은 없다. 스토리지 작업만으로 끝나는 처리에는 락을 직접 구현할 필요가 없다. `fetch()` 같은 스토리지 외 I/O를 `await`하는 동안에는 다른 요청이 끼어들 수 있으므로, `blockConcurrencyWhile()`이나 낙관적 락으로 보호한다.
3. **휘발성 없는 영속 스토리지**: 인스턴스에는 전용 내장 SQLite 스토리지(`ctx.storage`)가 갖춰져 있어, 메모리상의 변수뿐만 아니라 전용 SQLite 데이터베이스에도 동기적으로 읽고 쓸 수 있다.

## 개발자가 파악해야 할 특성

- 클라이언트 측에서는 바인딩을 통해 RPC(원격 프로시저 호출) 형식으로 직관적으로 메서드를 호출할 수 있다.
- 요청이 끊기면 인스턴스는 자동으로 메모리에서 퇴거(하이버네이션)되어 시간 과금이 발생하지 않게 된다. 다음 요청이 도착하면 `constructor()`가 다시 실행되어 인스턴스가 재생성된다.
- `ctx.storage.setAlarm()`을 호출하여 향후 특정 시점에 인스턴스를 자동으로 기동시켜 타이머 처리나 클린업을 실행할 수 있다.

## 인메모리 상태와 SQLite 스토리지의 차이

DO에는 상태를 두는 곳이 두 군데 있다. **클래스 필드(인메모리)** 와 **`ctx.storage`(SQLite)** 이다.

|             | 인메모리(클래스 필드)                                   | SQLite(`ctx.storage`)                          |
| ----------- | ------------------------------------------------------- | ---------------------------------------------- |
| 속도        | 가장 빠름(메모리 참조뿐)                                | 빠름(같은 머신의 디스크, 동기 API로 호출 가능) |
| 영속성      | 하이버네이션, 퇴거, 크래시, 코드 업데이트 시 **사라짐** | 재시작과 배포를 넘어 **유지됨**                |
| 적합한 용도 | 캐시, 연결 중인 WebSocket 목록, 쓰기 전 배치            | 원본 데이터 전반                               |

사라지는 주요 조건은 다음과 같다. 약 10초 유휴 상태로 하이버네이션에 들어갈 때(대기 중인 타이머, 표준 WebSocket, 끝나지 않은 I/O가 있으면 들어가지 않으며, 그 경우 70~140초 뒤 메모리에서 내려간다), 새 코드를 배포할 때(기본적으로 최대 5분의 유예), Workers 런타임이 업데이트될 때, 런타임이 배치 위치를 바꿀 때이다. 다시 호출되면 `constructor()`가 다시 실행되어 필드가 초기값으로 돌아간다.

따라서 원본은 항상 SQLite에 먼저 쓰고, 메모리는 읽기 속도를 높이는 데 쓴다. 생성자에서 SQLite를 읽어 필드를 채워 두는 것이 정석이다.

```ts
export class ChatRoom extends DurableObject {
  // 퇴거로 사라져도 되는 읽기 캐시
  recent: Message[] | null = null;

  addMessage(text: string) {
    // 먼저 영속화하고 캐시를 버린다
    this.ctx.storage.sql.exec("INSERT INTO messages (text) VALUES (?)", text);
    this.recent = null;
  }
}
```

## WebSocket과 Hibernation API

채팅처럼 연결을 계속 유지하는 용도는 DO에 잘 맞는다. 같은 이름의 DO에 모두가 연결되므로 브로드캐스트에 별도 장치가 필요 없다.

표준 `ws.accept()`를 쓰면 연결이 살아 있는 동안 DO가 메모리에 머물며 그 시간 내내 과금된다. **Hibernation API**는 `this.ctx.acceptWebSocket(ws)`로 연결을 맡기고 `webSocketMessage()` / `webSocketClose()` 핸들러로 받는다. 메시지가 없는 동안 DO는 연결을 끊지 않은 채 메모리에서 퇴거될 수 있다.

다만 퇴거되면 필드는 사라진다. 연결별 작은 정보(사용자 이름 등)는 `ws.serializeAttachment()`에 저장하고 깨어났을 때 `ws.deserializeAttachment()`로 복원한다. 이력은 SQLite에 둔다. 즉 Hibernation은 위 표의 구분을 지키는 것이 전제다.

다음 장 [Durable Object를 직접 작성하기](/lessons/durable-object-class)에서 코드를 고쳐 가며 두 상태의 차이를 확인할 수 있다.

에디터상의 `env.COUNTER`는 사이트가 마련한 Durable Object(이름은 `lesson-counter`)의 `increment()`와 `read()`를 중계하는 것으로, 프로덕션 바인딩처럼 `idFromName()`이나 `getByName()`으로 인스턴스를 고를 수는 없다. 카운터는 모두가 공유하며, 24시간 동안 호출되지 않으면 삭제된다. 코드를 반복 실행하면 프로세스가 재시작되어도 카운터가 계속 증가하는 동작을 확인할 수 있다.
