# Workers KV(키 밸류 스토어)

전 세계 수백 개 도시의 에지 캐시에서 자주 읽히는 키를 낮은 지연 시간으로 돌려준다——이렇게 들으면 만능 데이터 스토어처럼 보인다. 하지만 이 읽기 속도는 **최종 일관성(Eventual Consistency)**이라는 트레이드오프 위에 세워져 있다.

KV에 쓰기는 먼저 중앙 데이터 저장소에 들어간다. 각 로케이션의 캐시로 자동 전송되는 것은 아니며, 읽기 요청에 따라 캐시에 올라간다(푸시와 풀을 결합한 복제). 그래서 다른 로케이션에서는 캐시 만료 시간(`cacheTtl`, 기본 60초)이 지날 때까지 오래된 값이 보이고, 반영에 60초 이상 걸리기도 한다. 도쿄 에지에서 쓴 최신 값을 같은 순간 런던 에지에서 읽었을 때 보인다는 보장은 없다.

## 적합한 용도와 부적합한 용도

- **적합한 것**: 설정값, 기능 플래그, URL 리다이렉트 테이블, 세션 정보 캐시, OGP 메타데이터 캐시(쓰기가 극히 드물고 읽기 빈도가 압도적으로 높은 데이터).
- **무너지는 것**: 재고 할당 카운터, 잔액 관리, 실시간 참가자 수 카운트(직전 업데이트가 반영되지 않으면 사고로 이어지는 용도).

## 기본 조작 및 사양상의 한계

- `get(key)` / `put(key, value)` / `delete(key)` / `list({ prefix })`
- 하나의 키에 저장할 수 있는 값의 크기 상한은 25MB. JSON 문자열이나 바이너리 캐시 용도로는 충분한 용량이다.
- 목록 조회는 전방 일치(`prefix`) 검색만 지원한다. 전체 훑기나 복잡한 필터링에는 취약하다.
- 과금 구조는 읽기에 비해 쓰기 비용이 더 높게 책정되어 있다(100만 회 쓰기당 5달러). 쓰기 빈도가 높은 설계는 비용 부담이 커진다.

에디터상의 `env.KV`는 실제 KV를 RPC로 중계한 것으로, 프로덕션 바인딩과 인수와 반환값이 다르다. `put()`은 객체를 JSON 문자열로 저장한다(프로덕션의 `put()`이 받는 것은 문자열·ArrayBuffer·스트림뿐이다). `get()`은 항상 문자열을 반환하며 `type`을 지정할 수 없다. `put()`의 옵션과 `getWithMetadata()`도 사용할 수 없다. `list()`는 접두사(문자열 또는 `{ prefix }`)를 받아 키 이름의 배열을 반환한다(프로덕션에서는 `{ keys, list_complete, cursor }`). 저장 공간은 모든 사용자가 공유한다.

```js
await env.KV.put("user:1", "Alice");
const user = await env.KV.get("user:1"); // 'Alice'
const list = await env.KV.list({ prefix: "user:" }); // 에디터에서는 ["user:1", ...], 프로덕션에서는 { keys: [...], list_complete, cursor }
```
