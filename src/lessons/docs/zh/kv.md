# Workers KV（键值存储）

从全球数百个城市的边缘缓存中，以较低的延迟返回常被读取的键——听起来像是一个万能的数据存储。然而，这种读取速度是以**最终一致性（Eventual Consistency）**这一取舍为前提的。

写入 KV 的数据首先进入中央数据存储，并不会自动发送到每个位置的缓存，而是在被读取时才进入缓存（推送与拉取相结合的复制）。因此在其他位置，缓存过期（`cacheTtl`，默认 60 秒）之前看到的都是旧值，变更生效可能需要 60 秒甚至更久。无法保证在同一时刻，从伦敦边缘读取到的值与在东京边缘写入的最新值一致。

## 适用场景与不适用场景

- **适用场景**：配置值、功能标志、URL 重定向表、会话信息缓存、OGP 元数据缓存（写入极少，读取频率远高的数据）。
- **不适用场景**：库存拨付计数器、余额管理、实时参与人数统计（若未反映前次更新则会导致事故的场景）。

## 基本操作与规范限制

- `get(key)` / `put(key, value)` / `delete(key)` / `list({ prefix })`
- 单个键可存储的值的最大大小为 25MB。对于 JSON 字符串或二进制数据的缓存用途来说，这个容量绰绰有余。
- 列表检索仅支持前缀（`prefix`）查找。不擅长全量遍历或复杂的筛选。
- 计费结构设定为写入费用高于读取（每 100 万次写入 5 美元）。设计为高写入频率会增加成本。

编辑器中的 `env.KV` 通过 RPC 转发到真实的 KV，其参数和返回值与生产环境的绑定不同。`put()` 会把对象转换为 JSON 字符串后保存（生产环境的 `put()` 只接受字符串、ArrayBuffer 和流）。`get()` 始终返回字符串，不能指定 `type`。`put()` 的选项和 `getWithMetadata()` 同样不可用。`list()` 接收前缀（字符串或 `{ prefix }`），返回键名数组（生产环境返回 `{ keys, list_complete, cursor }`）。存储空间由所有用户共用。

```js
await env.KV.put("user:1", "Alice");
const user = await env.KV.get("user:1"); // 'Alice'
const list = await env.KV.list({ prefix: "user:" }); // 编辑器中为 ["user:1", ...]，生产环境中为 { keys: [...], list_complete, cursor }
```
