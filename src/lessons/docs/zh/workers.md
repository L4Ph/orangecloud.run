# Workers 的执行模型

如果你带着传统服务器开发的思维开始编写 Worker，最先让你失望的就是全局变量的生命周期。请求之间能共享的内存究竟在哪里？答案是：根本没有。

Worker 的本质，是一个**每次有事件到达时都会被调用的函数**。对于 HTTP 请求，`fetch(request, env, ctx)` 处理接收到的请求，返回的 `Response` 对象直接被发送给全球各地的客户端。

## 主导的 4 个约束

1. **状态不跨请求持久化。** 写入全局变量的值，仅在同一个 isolate 被偶然重复使用期间才会存在。如果下一个请求飞往另一个大洲的数据中心，那里的是全新的内存。想要持久化的数据，必须转移到 KV、D1、R2 或 Durable Objects 中。
2. **没有持久的磁盘，也没有可监听的套接字。** `node:fs` 能访问的是内存中的虚拟文件系统，只有 `/tmp` 可写，其内容按请求相互独立，请求结束后不会保留。也无法打开 Raw 套接字进行监听。与外部的通信通道仅限于 `fetch()`、建立出站 TCP 连接的 `connect()`，以及平台注入的绑定（如 `env.DB` 等）。
3. **计费取决于请求数和 CPU 时间。** 等待外部 API 响应的时间，以及因定时器而停止的时间，都不计入 CPU 时间。经过的时间本身也不计费。
4. **资源有上限。** 内存上限为每个 isolate 128MB。CPU 执行时间在免费额度下每次 10ms，即使在付费额度下，默认也限制为 30 秒（最多 5 分钟）。持续触及上限的执行会被终止，客户端会收到 Error 1102（`Worker exceeded resource limits`）。

## 限制值对比

| 项目     | 免费方案 | 付费方案                                   |
| -------- | -------- | ------------------------------------------ |
| 请求     | 10 万/日 | 无上限（含 1,000 万/月，超出部分按量计费） |
| CPU 时间 | 10ms/次  | 30 秒/次（最多 5 分钟）                    |
| 内存     | 128MB    | 128MB                                      |

“每次请求都准备好的、一次性且干净的房间”。有了这种思维模式，就能避免把状态放在全局变量里的错误。

```js
export default {
  async fetch(request, env, ctx) {
    // request: 接收到的 HTTP 请求
    // env: 绑定（KV、D1、秘密信息等）
    // ctx: waitUntil 等生命周期控制
    return new Response("hello from workers");
  },
};
```
