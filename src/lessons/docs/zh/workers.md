# Workers 的执行模型

如果你带着传统服务器开发的思维开始编写 Worker，最先让你失望的就是全局变量的生命周期。请求之间能共享的内存究竟在哪里？答案是：根本没有。

Worker 的本质，不过是一个**每次收到 HTTP 请求时都会被调用的纯函数**。`fetch(request, env, ctx)` 处理接收到的请求，返回的 `Response` 对象直接被发送给全球各地的客户端。

## 主导的 4 个约束

1. **状态不跨请求持久化。** 写入全局变量的值，仅在同一个 isolate 被偶然重复使用期间才会存在。如果下一个请求飞往另一个大洲的数据中心，那里的是全新的内存。想要持久化的数据，必须转移到 KV、D1、R2 或 Durable Objects 中。
2. **没有文件系统，也没有常驻套接字。** 无法将临时文件吐出到磁盘，也无法打开 Raw 套接字进行监听。与外部的通信通道仅限于 `fetch()` 以及平台注入的绑定（如 `env.DB` 等）。
3. **计费基于 CPU 时间。** 等待外部 API 响应的时间，以及因定时器而停止的时间，均不计费。这正是 Workers 作为微服务聚合代理能以极低成本运行的原因。
4. **硬件限制最先发威。** 内存上限为 128MB。CPU 执行时间在免费额度下每次 10ms，即使在付费额度下，默认也受限于 30 秒（最多 5 分钟）。如果运行无限循环，系统会毫不留情地强制终止该 isolate。

## 限制值对比

| 项目     | 免费方案 | 付费方案                |
| -------- | -------- | ----------------------- |
| 请求     | 10 万/日 | 1,000 万/月 + 按量计费  |
| CPU 时间 | 10ms/次  | 30 秒/次（最多 5 分钟） |
| 内存     | 128MB    | 128MB                   |

“每次请求都准备好的、一次性且干净的房间”。只要养成这种思维模式，就不会掉入无服务器（serverless）的陷阱。

```js
export default {
  async fetch(request, env, ctx) {
    // request: 接收到的 HTTP 请求
    // env: 绑定（KV、D1、秘密信息等）
    // ctx: waitUntil 等生命周期控制
    return new Response("hello from workers");
  },
};
```
