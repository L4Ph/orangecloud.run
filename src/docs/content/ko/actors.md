# Durable Objects와 Actor 모델

Durable Objects(DO)는 연산과 스토리지를 결합한 특별한 Worker이다. 그 구조는 동시 컴퓨팅의 고전 이론인 **Actor 모델(액터 모델)**의 관점으로 설명할 수 있으며, Cloudflare 문서도 각 DO를 Actor로 볼 수 있다고 설명한다. 이 관점을 알면 DO가 객체 지향 클래스 구문으로 정의되는 이유와, 하나의 인스턴스 안에서 JavaScript가 동시에 실행되지 않는 이유를 이해하기 쉽다. 다만 `await` 사이에 다른 처리가 끼어들 수 있다는 점 등, 엄밀한 Actor 모델과 다른 부분도 있다(마지막 절에서 설명한다).

## Actor 모델이 부과하는 4가지 규약

Erlang의 프로세스나 Akka의 Actor로 대표되는 Actor 모델은 분산 환경에서 안전하게 상태를 유지하기 위해 다음과 같은 규약을 정한다.

1. **유일한 동일성(Identity)**: 모든 액터는 고유한 식별 이름(ID 또는 이름)으로 지칭된다. 동일한 이름을 지정하는 한, 물리적으로 동일한 엔티티에 도달한다.
2. **사유화된 상태(Private State)**: 상태는 액터 내부에만 닫혀 있으며, 외부 프로세스가 직접 메모리를 엿볼 수 없다.
3. **메시지 통신(Message Passing)**: 액터 간의 모든 상호작용은 비동기 메시지의 송수신으로만 이루어진다. 수신된 메시지는 받은 편지함에 순차적으로 쌓인다.
4. **한 번에 하나만 처리(Turn-based Processing)**: 액터는 받은 편지함에서 메시지를 하나씩 꺼내 순서대로 처리한다. 내부에서 동시에 여러 처리가 실행되지 않으므로, 경합 상태(Race Condition)가 발생할 수 없다.

이 규약 덕분에 공유 메모리의 배타적 제어나 분산 락의 복잡함을 피할 수 있고, 상태의 물리적 배치 위치(로케이션 투명성)도 플랫폼에 맡길 수 있다.

## Durable Objects와 Actor의 대응 관계

| Actor 모델의 개념    | Cloudflare Durable Objects의 구현                                                                                                              |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 액터의 식별 이름     | `env.ROOM.idFromName('room-1')`로 생성되는 고유 ID                                                                                             |
| 사유화된 상태        | `this.ctx.storage`(내장 SQLite) 및 `this` 인스턴스 변수                                                                                        |
| 메시지               | 클래스에 정의된 타입 지정 RPC 메서드 또는 `fetch()`                                                                                            |
| 받은 편지함과 직렬화 | 단일 스레드로 실행. 스토리지 외 I/O(`fetch()` 등)를 `await`하는 동안에는 다른 요청이 끼어들 수 있다                                            |
| 액터의 소멸과 부활   | 약 10초 유휴 상태가 되면 메모리에서 퇴거(Hibernation). 다음 이벤트에서 `constructor()`가 다시 실행되어 재생성되며, 메모리 상의 상태는 사라진다 |
| 물리적 배치 위치     | 원칙적으로 해당 엔티티에 처음 요청을 보낸 에지(Colo) 근처                                                                                      |

## 왜 함수가 아니라 클래스로 작성하는가

클래스 구문을 쓰는 이유는 **클래스가 '동작의 정의 단위'이자 동시에 DO 네임스페이스와 그 수명 주기(생성·이름 변경·삭제·이전)를 관리하는 단위이기 때문**이다. 배포의 단위는 Worker이며 클래스가 아니다.

동일한 동작을 가진 액터 엔티티를 방 이름이나 사용자 이름별로 수만 개 생성한다. 이 요구사항을 충족하려면 동작을 나타내는 '타입(클래스)'과 개별 상태를 유지하는 '인스턴스(이름)'를 명확히 분리해야 한다.

```ts
export class ChatRoom extends DurableObject {
  async join(user: string) {
    const members = (await this.ctx.storage.get<string[]>("members")) ?? [];
    if (!members.includes(user)) {
      members.push(user);
      await this.ctx.storage.put("members", members);
    }
    return members;
  }

  async alarm() {
    // `setAlarm()`으로 설정한 시각에 깨어나 이 DO에 저장된 데이터를 모두 지운다
    await this.ctx.storage.deleteAll();
  }
}
```

RPC 메서드 `join`에 여러 클라이언트가 동시에 접근해도, 배열을 읽고 쓰는 사이에 다른 처리가 끼어들어 데이터가 손상되는 일은 없다. 스토리지 작업을 `await`하는 동안에는 입력 게이트(input gate)가 다른 이벤트의 전달을 막기 때문이다.

## 고려해야 할 처리량 경계선

- **Durable Object 하나는 단일 스레드로 동작하며, 단순한 처리라면 초당 500~1,000건 정도가 기준이다**(객체당 소프트 한도는 초당 1,000건이며, 초과하면 과부하 오류가 반환된다). 수십만 건의 접근을 하나의 DO 인스턴스에 집중시키면 당연히 병목 현상이 발생한다. 방별, 테넌트별, 사용자 ID별로 세밀하게 인스턴스를 분할 배치하는 설계가 기본이 된다.
- **스토리지 외 I/O(`fetch()`나 R2 등)를 `await`하는 동안에는 다른 요청의 처리가 끼어들 수 있다(Interleaving)**. 스토리지 작업을 `await`하는 동안에는 입력 게이트가 다른 이벤트의 전달을 막으므로 끼어들지 못한다. 끼어들기로 상태의 불변 조건이 깨질 수 있는 처리는 `blockConcurrencyWhile()`이나, 버전 번호를 확인한 뒤 쓰는 낙관적 락으로 보호한다.
- 하이버네이션이 가능한 상태로 유휴인 인스턴스에는 시간(GB 초) 과금이 발생하지 않는다. 대기 중인 타이머나 표준 WebSocket(`ws.accept()`)이 있으면 유휴 상태에서도 과금이 계속된다. 상시 연결되는 WebSocket은 Hibernation API를 쓰면 연결을 유지한 채 대기 중의 시간 과금을 피할 수 있다.
