# 에지에서의 상태 설계(스토리지 선택 기준)

Cloudflare Workers의 인스턴스 하나는 여러 요청을 동시에 처리할 수 있다. 어떤 요청이 같은 인스턴스에 도착할지는 보장되지 않으며, 인스턴스도 언제 퇴거될지 알 수 없다. 따라서 메모리 상의 변수에 상태를 의존할 수 없고, 데이터는 외부 스토리지 계층에 맡겨야 한다.

문제는 '어떤 스토리지를 선택할 것인가'이다. 이 선택을 잘못하면 직전 쓰기 내용을 읽을 수 없는 '유령 데이터' 현상이나, 인덱스 미설정으로 인한 쿼리 비용의 폭발, 단일 인스턴스 과부하로 인한 병목 현상이 발생한다. 선택의 판단 기준은 **일관성 모델·데이터 크기·과금 트리거**의 세 가지 점으로 요약된다.

## 일관성 모델을 통한 1차 선별

| 스토리지            | 일관성 수준                                                                                    | 최적의 유스케이스                          | 위험한 오용                           |
| ------------------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------ | ------------------------------------- |
| **Workers KV**      | 최종 일관성(다른 로케이션에 반영되기까지 60초 이상 걸릴 수 있음)                               | 설정값, 기능 플래그, URL 리다이렉트 테이블 | 엄격한 카운터, 잔액, 구매 직후의 세션 |
| **D1**              | 기본은 단일 프라이머리(레플리카 읽기는 활성화와 Sessions API 필요)                             | 구조화된 데이터, 관계 검색, 집계           | 큰 바이너리 저장(한 행 2MB가 상한)    |
| **Cloudflare R2**   | 강일관성(객체 단위)                                                                            | 이미지, 동영상, 로그, 백업                 | 수 킬로바이트의 세밀한 빈번 업데이트  |
| **Durable Objects** | 단일 인스턴스, 스토리지는 강한 일관성(스토리지 외 I/O를 기다리는 동안 끼어들기 가능)           | 채팅방, 티켓 재고, 분산 락                 | 모든 요청의 무차별적 집약             |
| **Hyperdrive**      | 연결 풀과 읽기 쿼리 캐시(기본 활성화. 기본 `max_age` 60초 동안은 오래된 결과가 반환될 수 있음) | PostgreSQL / MySQL과의 고속 통신           | 쓰기 직후의 읽기(캐시 활성화 시)      |

"세계에서 유일하게 최신 값을 경합 없이 업데이트하고 싶다"면 Durable Objects를, 관계나 집계가 필요하다면 D1을 선택한다. 섣불리 KV에 카운터를 두면, 서로 다른 로케이션에서의 동시 쓰기가 서로를 덮어써서(나중에 쓴 쪽이 우선) 증가분이 유실된다.

## 크기 제약과 과금 구조의 함정

- **Workers KV**: 키당 25MB. 읽기는 100만 회당 0.5달러이지만 쓰기는 100만 회당 5달러로 단가가 높으므로 업데이트 빈도가 높은 설계는 피한다.
- **D1**: 발행한 쿼리 수가 아니라 **읽은(스캔한) 행 수와 쓴 행 수**로 과금된다. `CREATE INDEX`가 없는 `WHERE` 쿼리는 모든 행을 스캔해 읽기 행 수를 끌어올린다. 한편 인덱스는 쓰기마다 쓰기 행 수를 하나 늘린다.
- **Cloudflare R2**: 저장 용량과 작업 횟수(Class A / Class B)로 과금되며, R2에서 직접 내보내는 **하향 데이터 전송(Egress)은 무료**이다. 다만 읽기는 Class B 작업으로 과금되고, Infrequent Access 클래스에는 데이터 조회 요금도 붙는다. 전송량이 큰 정적 파일은 작업 횟수까지 계산해 본 뒤 R2에 둔다.
- **Durable Objects**: 요청 수와 실행 시간(실제 경과 시간을 128MB 고정으로 GB 초로 환산)에 따른 종량제이며, SQLite 스토리지는 읽은 행 수·쓴 행 수·저장 용량으로도 과금된다. 하이버네이션이 가능한 상태로 유휴인 동안에는 시간 과금이 발생하지 않는다.

## 대표적인 안티패턴

1. **세션 저장에 KV를 채택하고, 로그인 직후 리다이렉트 대상에서 검증하기**: 리다이렉트 대상이 다른 로케이션에서 처리되면 캐시가 만료될 때까지 오래된 값(또는 키 없음)이 반환될 수 있어 인증에 실패한다. 직후의 상태 전이는 암호화 쿠키 등의 상태 없는 수단과 결합한다.
2. **D1의 컬럼에 이미지나 PDF 바이너리를 직접 저장하기**: 한 행(BLOB 하나)의 상한은 2MB이며 이미지나 PDF는 넘기 쉽다. 데이터베이스 전체의 상한도 10GB(무료 플랜은 500MB)이다. 참고로 읽기 행 수 과금은 행의 크기와 무관하다(1KB 행도 100KB 행도 1행). 바이너리 실체는 R2에 두고, D1에는 객체 키만 기록한다.
3. **모든 트래픽을 하나의 Durable Object 인스턴스로 집중시키기**: 직렬화 메커니즘이 역효과를 내어, 전 세계에서 오는 요청이 단일 노드에서 순번을 기다리게 되어 지연 시간이 급격히 악화된다. 테넌트 단위나 사용자 단위로 ID를 세밀하게 분산시켜야 한다.

## 견고한 조합 패턴

- **R2(실체 파일) + D1(메타데이터 인덱스)**: 이미지나 문서의 본체는 전송 무료인 R2에 맡기고, 태그나 업데이트 시각, 소유자 ID는 D1에서 인덱스 검색한다.
- **Durable Objects(일관성 검문소) + Queues(비동기 소화)**: 주문 할당이나 재고 감산은 DO에서 직렬화하여 일관성을 보장하고, 시간이 걸리는 결제 처리나 이메일 발송은 Queues에 맡긴다.
