# 에지에서의 상태 설계(스토리지 선택 기준)

Cloudflare Workers는 요청마다 독립된 메모리 공간에서 실행된다. 메모리에 상태를 유지하는 것이 허용되지 않으므로, 데이터는 필연적으로 외부 스토리지 계층으로 위임해야 한다.

문제는 '어떤 스토리지를 선택할 것인가'이다. 이 선택을 잘못하면 직전 쓰기 내용을 읽을 수 없는 '유령 데이터' 현상이나, 인덱스 미설정으로 인한 쿼리 비용의 폭발, 단일 인스턴스 과부하로 인한 병목 현상이 발생한다. 선택의 판단 기준은 **일관성 모델·데이터 크기·과금 트리거**의 세 가지 점으로 요약된다.

## 일관성 모델을 통한 1차 선별

| 스토리지            | 일관성 수준                            | 최적의 유스케이스                          | 위험한 오용                            |
| ------------------- | -------------------------------------- | ------------------------------------------ | -------------------------------------- |
| **Workers KV**      | 결과 일관성(최대 60초의 전파 지연)     | 설정값, 기능 플래그, URL 리다이렉트 테이블 | 엄격한 카운터, 잔액, 구매 직후의 세션  |
| **D1**              | 프라이머리 쓰기, 레플리카 읽기         | 구조화된 데이터, 관계 검색, 집계           | 수 메가바이트를 초과하는 바이너리 저장 |
| **Cloudflare R2**   | 강일관성(객체 단위)                    | 이미지, 동영상, 로그, 백업                 | 수 킬로바이트의 세밀한 빈번 업데이트   |
| **Durable Objects** | 단일 노드에서 완전 직렬화(강한 일관성) | 채팅방, 티켓 재고, 분산 락                 | 모든 요청의 무차별적 집약              |
| **Hyperdrive**      | 기존 관계형 DB로의 연결 풀             | PostgreSQL / MySQL과의 고속 통신           | -                                      |

"세계에서 유일하게 최신 값을 경합 없이 업데이트하고 싶다"면 Durable Objects를, 관계나 집계가 필요하다면 D1을 선택한다. 섣불리 KV에 카운터를 두면, 서로 다른 에지에서의 동시 쓰기로 인해 확실히 값의 조상 회귀가 발생한다.

## 크기 제약과 과금 구조의 함정

- **Workers KV**: 키당 25MB. 읽기 비용은 극히 낮지만, 쓰기 단가(100만 회당 5달러)가 상대적으로 높으므로 업데이트 빈도가 높은 설계는 피한다.
- **D1**: 발행 쿼리 수가 아니라 **탐색한 행 수**로 과금된다. `CREATE INDEX`가 없는 `WHERE` 쿼리는 모든 행을 훑어보며 즉시 과금액을 끌어올린다.
- **Cloudflare R2**: 저장 용량과 조작 요청 수만 과금 대상이며, **하향 데이터 전송(Egress)이 완전히 무료**이다. 전송 트래픽이 큰 정적 파일은 망설임 없이 R2에 둔다.
- **Durable Objects**: 요청 수 및 사용 메모리 시간(GB 초)의 종량제. 액세스가 없는 기간에는 자동 하이버네이션으로 과금이 중단된다.

## 대표적인 안티패턴

1. **세션 저장에 KV를 채택하고, 로그인 직후 리다이렉트 대상에서 검증하기**: 쓰기 전파 지연으로 인해 직후 읽기 시 키를 찾지 못해 인증 실패가 발생한다. 직후의 상태 전이는 암호화 쿠키 등의 상태 없는 수단과 결합해야 한다.
2. **D1의 컬럼에 이미지나 PDF 바이너리를 직접 저장하기**: 레코드 행의 크기가 비대해져 검색 시 읽기 행 수 과금과 I/O 대역폭을 낭비한다. 바이너리 실체는 R2로 옮기고, D1에는 객체 키만 기록하는 것이 철칙이다.
3. **모든 트래픽을 하나의 Durable Object 인스턴스로 집중시키기**: 직렬화 메커니즘이 역효과를 내어, 전 세계에서 오는 요청이 단일 노드에서 순번을 기다리게 되어 지연 시간이 급격히 악화된다. 테넌트 단위나 사용자 단위로 ID를 세밀하게 분산시켜야 한다.

## 견고한 조합 패턴

- **R2(실체 파일) + D1(메타데이터 인덱스)**: 이미지나 문서의 본체는 전송 무료인 R2에 맡기고, 태그나 업데이트 시각, 소유자 ID는 D1에서 인덱스 검색한다.
- **Durable Objects(일관성 검문소) + Queues(비동기 소화)**: 주문 할당이나 재고 감산은 DO에서 직렬화하여 즉각적으로 일관성을 보장하고, 무거운 결제 처리나 이메일 배포는 Queues로 즉시 흘려보낸다.
