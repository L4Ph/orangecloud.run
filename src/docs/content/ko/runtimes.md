# 런타임 구조 비교 (Node.js와 V8 isolate)

서버 측 JavaScript의 역사는 오랫동안 Node.js의 아키텍처와 동일시되어 왔다. 하지만 엣지 컴퓨팅이 요구하는 '극소의 기동 시간', '극도로 높은 수용 밀도', '안전한 멀티테넌트 격리' 앞에서 Node.js의 전제 구조는 큰 걸림돌이 된다.

Cloudflare Workers를 뒷받침하는 **V8 isolate**가 무엇을 걷어내고 무엇을 남겼는지 이해함으로써, 엣지에서의 정확한 설계 판단이 가능해진다.

## 프로세스 모델과 격리 아키텍처의 근본적 차이

Node.js는 기본적으로 하나의 OS 프로세스에 하나의 V8 인스턴스(isolate)를 할당한다. `worker_threads`를 쓰면 같은 프로세스에 isolate를 늘릴 수 있지만, isolate마다 libuv 이벤트 루프가 하나씩 붙는다. 그 외부에는 libuv의 스레드 풀과 소켓 관리 메커니즘이 얽혀 있다. 이 구조는 하나의 프로세스를 영속적으로 상주시키는 것을 전제로 하며, 요청마다 프로세스를 신설·파기하는 운영 방식에는 맞지 않는다.

```
[Node.js의 프로세스 구조]
OS 프로세스 ── libuv (C / 스레드 풀 / 파일 I/O / 네트워크 소켓)
             └── 단일 V8 인스턴스 (모든 요청에서 힙·상태를 공유)

[Workers의 isolate 구조]
런타임 프로세스 ── 격리 경계 (메모리 보호·권한 샌드박스)
                 ├── isolate A (사용자 A의 힙 / 독립 메모리 공간)
                 ├── isolate B (사용자 B의 힙 / 독립 메모리 공간)
                 └── isolate C (사용자 C의 힙 / 독립 메모리 공간)
```

Cloudflare Workers는 OS 프로세스 레이어를 은폐하고, **V8 isolate 단독**을 실행의 기본 단위로 취급한다. 런타임 인스턴스 하나는 메모리 공간이 서로 분리된 수백에서 수천 개의 isolate를 오가며 실행할 수 있다.

isolate 바깥의 메모리에 접근하는 것은 V8이 막는다. Cloudflare는 여기에 더해 Linux의 namespace와 seccomp로 프로세스가 파일 시스템과 네트워크에 접근하지 못하게 하고, 신뢰 수준이 다른 Worker를 서로 다른 런타임 인스턴스로 나눈다. V8에도 버그가 있으므로, Cloudflare는 패치 공개부터 프로덕션 배포까지를 24시간 미만으로 유지한다.

## 컨테이너와 isolate의 기동 시간

컨테이너(Docker 등)의 기동에는 컨테이너 이미지의 레이어 압축 해제, Linux 네임스페이스(Namespace) 초기화, 가상 네트워크 인터페이스 구성, 그리고 게스트 프로세스 기동이라는 일련의 단계가 필요하다. Cloudflare Containers에서는 각 인스턴스가 전용 커널을 가진 Firecracker microVM 안에서 동작하며, 콜드 스타트는 1~3초 정도인 경우가 많다(이미지 크기와 코드에 따라 달라진다).

이에 반해 isolate는 이미 동작 중인 런타임 안에 만들기만 하면 되고, 프로세스도 가상 머신도 기동하지 않는다. Cloudflare는 isolate가 컨테이너나 가상 머신 위의 Node 프로세스보다 약 100배 빠르게 기동한다고 설명한다. 다만 Worker의 콜드 스타트에는 스크립트 가져오기, 컴파일, 최상위 코드 실행이 포함된다. 스크립트가 크고 최상위 처리가 무거울수록 길어진다. 기동 시간에는 1초의 상한이 있다.

## 아키텍처 선정 경계

| 처리 성격                                  | 최적의 선택지                          | 근거                                                                                                |
| ------------------------------------------ | -------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Web API, 경량 비즈니스 로직, 데이터 중계   | **V8 isolate(Workers)**                | isolate는 기동이 빠르고, 아이들 비용이 제로                                                         |
| Linux 바이너리를 실행하는 처리(FFmpeg 등)  | **Cloudflare Containers**              | 완전한 Linux 커널과 바이너리 실행 환경이 필요                                                       |
| 헤드리스 브라우저 조작(Playwright)         | **Browser Run**                        | Worker에서 Playwright로 조작할 수 있음                                                              |
| 장시간 배치                                | **Workflows / Queues / Cron Triggers** | Cron과 Queue consumer는 15분까지. Workflows는 1단계의 경과 시간에 상한이 없음(CPU 시간 상한은 남음) |
| 외부와의 연결 대기(DB 쿼리, 외부 REST API) | **V8 isolate(Workers)**                | 요청 수와 CPU 시간으로 과금되며, 네트워크 대기 시간은 과금되지 않는다                               |
| 단일 리소스로의 직렬화 및 배타적 제어      | **Durable Objects**                    | 전 세계에서 하나의 인스턴스로 요청을 집약                                                           |

Node.js용 라이브러리를 가져올 때는 `nodejs_compat` 호환 플래그를 사용한다. 호환 날짜(compatibility date)가 2026-08-04 이후인 Worker에서는 이 플래그가 기본으로 활성화된다. `Buffer`, `crypto`, `events`에 더해 `process`, `node:fs`, `node:http`, `node:net`, `node:zlib` 등이 내장되어 있으며, `child_process`처럼 import만 되고 동작하지 않는 모듈도 있다. 다만 `node:fs`의 실체는 메모리상의 가상 파일 시스템이고, 쓸 수 있는 `/tmp`는 요청마다 독립된 임시 영역이다. 영속적인 로컬 디스크를 전제로 한 설계는 성립하지 않는다.
