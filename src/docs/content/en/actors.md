# Durable Objects and the Actor Model

Durable Objects are often described as "small servers with state." However, their true essence is a pure implementation of the **Actor Model**, a classic theory of concurrent computing. Understanding this background makes the necessity of defining DOs using object-oriented class syntax and serializing method calls one by one crystal clear.

## Four Conventions Imposed by the Actor Model

The Actor Model—epitomized by Erlang's processes and Akka's Actors—establishes the following conventions to safely maintain state in distributed environments:

1. **Unique Identity**: Every actor is referred to by a unique identifier (ID or name). As long as the same name is specified, the system reaches the physically identical entity.
2. **Private State**: State is confined entirely within the actor; external processes cannot directly peer into memory.
3. **Message Passing**: All interactions between actors occur solely through the sending and receiving of asynchronous messages. Incoming messages are stacked in order in an inbox.
4. **Turn-based Processing**: Actors retrieve messages from the inbox one at a time and process them sequentially. Since no multiple processes run concurrently internally, race conditions cannot occur.

The greatest advantage is the ability to leave the physical location of state (location transparency) to the platform, without having to worry about the complexities of shared-memory concurrency control or distributed locking.

## Correspondence Between Durable Objects and the Actor Model

| Actor Model Concept             | Cloudflare Durable Objects Implementation                                                           |
| ------------------------------- | --------------------------------------------------------------------------------------------------- |
| Actor Identifier                | Unique ID generated by `env.ROOM.idFromName('room-1')`                                              |
| Private State                   | `this.ctx.storage` (built-in SQLite) and `this` instance variables                                  |
| Messages                        | Typed RPC methods defined in the class, or `fetch()`                                                |
| Inbox and Serialization         | Fully guaranteed by the infrastructure layer. Method calls are executed sequentially, one at a time |
| Actor Disappearance and Respawn | Hibernation when memory runs low, and immediate restoration upon the next request                   |
| Physical Location               | In principle, near the edge (Colo) where the request was first sent to that entity                  |

## Why Write with Classes Instead of Functions?

The reason class syntax is enforced is that **classes are the "unit of behavior definition" and, simultaneously, the "smallest unit for deployment and schema migration."**

If one were to create tens of thousands of actor entities with the same behavior—one for each room name or username—they would have to clearly separate the "type (class)" representing the behavior from the "instance (name)" holding the individual state.

```ts
export class ChatRoom extends DurableObject {
  async join(user: string) {
    const members = (await this.ctx.storage.get<string[]>("members")) ?? [];
    if (!members.includes(user)) {
      members.push(user);
      await this.ctx.storage.put("members", members);
    }
    return members;
  }

  async alarm() {
    // Wake up at the set alarm time and clear out old messages
    await this.ctx.storage.deleteAll();
  }
}
```

Even if the RPC method `join` is flooded with simultaneous accesses from multiple clients, it is reliably executed sequentially, one at a time internally. There is no concern that data will be corrupted because another process interrupts the gap between array reads and writes.

## Throughput Considerations

- **Single-instance throughput is limited to one CPU core.** Concentrating hundreds of thousands of accesses into a single DO instance will naturally create a bottleneck. The fundamental design is to partition and place instances meticulously by room, tenant, or user ID.
- **While waiting for asynchronous processing with `await`, other messages may be interleaved (Interleaving).** When maintaining state consistency, one must be mindful of whether state invariants are violated before and after the `await`.
- Idle instances automatically transition to hibernation, reducing CPU cost to zero. When handling always-on WebSockets, using the Hibernation API avoids incurring connection maintenance fees.
