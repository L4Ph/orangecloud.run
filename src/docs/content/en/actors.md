# Durable Objects and the Actor Model

A Durable Object (DO) is a special kind of Worker that combines compute with storage. Its design can be explained through the **Actor Model**, a classic theory of concurrent computing, and Cloudflare's documentation also says that each DO can be seen as an Actor. Seeing it this way makes it easier to understand why DOs are defined with object-oriented class syntax and why JavaScript never runs simultaneously inside a single instance. However, DOs differ from the strict Actor Model in places, for example in that other requests can run while one is waiting at an `await` (covered in the last section).

## Four Conventions Imposed by the Actor Model

The Actor Model—epitomized by Erlang's processes and Akka's Actors—establishes the following conventions to safely maintain state in distributed environments:

1. **Unique Identity**: Every actor is referred to by a unique identifier (ID or name). As long as the same name is specified, the system reaches the physically identical entity.
2. **Private State**: State is confined entirely within the actor; external processes cannot directly peer into memory.
3. **Message Passing**: All interactions between actors occur solely through the sending and receiving of asynchronous messages. Incoming messages are stacked in order in an inbox.
4. **Turn-based Processing**: Actors retrieve messages from the inbox one at a time and process them sequentially. Since no multiple processes run concurrently internally, race conditions cannot occur.

These conventions avoid the complexity of shared-memory concurrency control and distributed locking, and leave the physical location of state (location transparency) to the platform.

## Correspondence Between Durable Objects and the Actor Model

| Actor Model Concept             | Cloudflare Durable Objects Implementation                                                                                                                  |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Actor Identifier                | Unique ID generated by `env.ROOM.idFromName('room-1')`                                                                                                     |
| Private State                   | `this.ctx.storage` (built-in SQLite) and `this` instance variables                                                                                         |
| Messages                        | Typed RPC methods defined in the class, or `fetch()`                                                                                                       |
| Inbox and Serialization         | Runs on a single thread. Other requests can run while a call awaits non-storage I/O (such as `fetch()`)                                                    |
| Actor Disappearance and Respawn | Evicted from memory after about 10 seconds idle (Hibernation). The next event reruns `constructor()` and recreates the object, and in-memory state is lost |
| Physical Location               | In principle, near the edge (Colo) where the request was first sent to that entity                                                                         |

## Why Write with Classes Instead of Functions?

Class syntax is used because **a class is the "unit of behavior definition" and, at the same time, the unit that manages a DO namespace and its lifecycle (create, rename, delete, transfer)**. The unit of deployment is the Worker, not the class.

If one were to create tens of thousands of actor entities with the same behavior—one for each room name or username—they would have to clearly separate the "type (class)" representing the behavior from the "instance (name)" holding the individual state.

```ts
export class ChatRoom extends DurableObject {
  async join(user: string) {
    const members = (await this.ctx.storage.get<string[]>("members")) ?? [];
    if (!members.includes(user)) {
      members.push(user);
      await this.ctx.storage.put("members", members);
    }
    return members;
  }

  async alarm() {
    // Wake up at the time set with `setAlarm()` and delete all data stored in this DO
    await this.ctx.storage.deleteAll();
  }
}
```

Even if multiple clients call the RPC method `join` at the same time, no other request can slip in between the array read and the array write and corrupt the data. While a storage operation is being awaited, the runtime's input gate holds back other events.

## Throughput Considerations

- **A single Durable Object runs on one thread, and about 500–1,000 requests per second is the guideline for simple operations** (the soft limit per object is 1,000 requests per second, and beyond that overload errors are returned). Concentrating hundreds of thousands of accesses into a single DO instance will naturally create a bottleneck. The fundamental design is to partition and place instances meticulously by room, tenant, or user ID.
- **While awaiting non-storage I/O (such as `fetch()` or R2), the processing of other requests can interleave (Interleaving)**. While awaiting a storage operation, the input gate holds back other events, so nothing slips in. Protect code whose state invariants an interleaving request could break with `blockConcurrencyWhile()` or an optimistic lock that checks a version number before writing.
- An idle instance that is eligible for hibernation incurs no duration (GB-second) charges. Pending timers or a standard WebSocket (`ws.accept()`) keep the charges running even while idle. For always-on WebSockets, the Hibernation API lets you keep connections open without paying duration charges while waiting.
