# 边缘端的状态设计（存储选择标准）

单个 Cloudflare Workers 实例可能同时处理多个请求。哪些请求会到达同一个实例无法保证，实例也随时可能被回收。因此不能依赖内存中的变量保存状态，数据必须交给外部存储层。

问题在于“选择哪种存储”。如果选择错误，会导致前一次写入无法读取的“幽灵数据”现象、因未设置索引而引发的查询费用爆炸，以及单个实例过载导致的瓶颈。选择的判断标准可归纳为 **一致性模型、数据大小、计费触发机制** 这三点。

## 基于一致性模型的初步筛选

| 存储                | 一致性级别                                                              | 最佳用例                         | 危险误用                           |
| ------------------- | ----------------------------------------------------------------------- | -------------------------------- | ---------------------------------- |
| **Workers KV**      | 最终一致性（在其他位置可能需要 60 秒或更久才能看到变更）                | 配置值、功能标志、URL 重定向表   | 严格的计数器、余额、购买后的会话   |
| **D1**              | 默认为单个主库（副本读取需要启用并配合 Sessions API）                   | 结构化数据、关系查询、聚合       | 存储大型二进制数据（单行上限 2MB） |
| **Cloudflare R2**   | 强一致性（按对象）                                                      | 图片、视频、日志、备份           | 数千字节的细粒度频繁更新           |
| **Durable Objects** | 单个实例，存储为强一致性（等待非存储 I/O 期间其他请求可能插入）         | 聊天室、工单库存、分布式锁       | 对所有请求进行无差别聚合           |
| **Hyperdrive**      | 连接池加读取查询缓存（默认启用；默认 60 秒 `max_age` 内可能返回旧结果） | 与 PostgreSQL / MySQL 的高速通信 | 写入后立即读取（启用缓存时）       |

如果“希望在无竞争的情况下更新全球唯一的最新值”，请选择 Durable Objects；如果需要关系或聚合，请选择 D1。如果随意在 KV 中放置计数器，来自不同位置的并发写入会相互覆盖（后写入者生效），计数的增量就会丢失。

## 大小限制与计费结构的陷阱

- **Workers KV**：每个键 25MB。读取每 100 万次 0.5 美元，但写入每 100 万次 5 美元，单价较高，因此应避免更新频率高的设计。
- **D1**：计费基于**读取（扫描）的行数和写入的行数**，而非发出的查询数。没有 `CREATE INDEX` 的 `WHERE` 查询会扫描所有行，推高读取行数。而索引会使每次写入多计一行写入。
- **Cloudflare R2**：按存储容量和操作次数（Class A / Class B）计费，从 R2 直接发出的**下行数据传输（Egress）免费**。但读取会按 Class B 操作计费，Infrequent Access 存储类别还要收取数据检索费。对于传输流量较大的静态文件，先估算操作次数，再放入 R2。
- **Durable Objects**：按请求数和运行时间（按实际经过的时间，以固定 128MB 折算为 GB 秒）计费，SQLite 存储还按读取行数、写入行数和存储容量计费。处于可休眠状态的空闲期间，不产生时长费用。

## 代表性反模式

1. **采用 KV 保存会话，并在登录后立即在重定向目标端进行验证**：如果重定向目标由另一个位置处理，在缓存过期之前可能返回旧值（或找不到键），导致认证失败。随后的状态转移应结合加密 Cookie 等无状态（stateless）手段。
2. **在 D1 的列中直接存储图片或 PDF 的二进制数据**：单行（单个 BLOB）上限为 2MB，图片和 PDF 很容易超出；整个数据库的上限也只有 10GB（免费方案为 500MB）。另外，读取行数的计费与行的大小无关（1KB 的行和 100KB 的行都算一行）。二进制实体应放在 R2 中，D1 中只记录对象键。
3. **将所有流量集中到单个 Durable Object 实例上**：串行化机制反而产生反效果，来自全球的请求在单个节点上排队，导致延迟急剧恶化。必须按租户或用户单位细分 ID。

## 稳健的组合模式

- **R2（实体文件）+ D1（元数据索引）**：将图片或文档的主体存放在免费传输的 R2 中，而将标签、更新日期、所有者 ID 在 D1 中进行索引检索。
- **Durable Objects（一致性关卡）+ Queues（异步处理）**：订单分配或库存扣除在 DO 中串行化以确保一致性，而耗时的支付处理或邮件发送则交给 Queues。
