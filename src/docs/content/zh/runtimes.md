# 运行时架构对比（Node.js 与 V8 isolate）

服务端 JavaScript 的历史长期以来一直被视为与 Node.js 架构相同。然而，面对边缘计算所要求的“极短启动时间”、“极高容量密度”以及“安全的多租户隔离”，Node.js 的基础架构成为了巨大的绊脚石。

通过理解支撑 Cloudflare Workers 的 **V8 isolate** 剔除了哪些部分、保留了哪些部分，可以在边缘环境下做出精准的设计决策。

## 进程模型与隔离架构的根本差异

Node.js 为单个 OS 进程分配一个 V8 实例。在其外部，分布着 libuv 的事件循环、多线程池、文件描述符表以及原始套接字的管理机制。这种结构以单个进程持久驻留为前提，完全无法承受每次请求都需新建并销毁进程的运作方式。

```
[Node.js 的进程结构]
OS 进程 ── libuv (C++ / 线程池 / 文件 I/O / 网络套接字)
             └── 单个 V8 实例 (所有请求共享堆与状态)

[Workers 的 isolate 结构]
单个宿主进程 ── 隔离边界 (内存保护、权限沙箱)
                      ├── isolate A (用户 A 的堆 / 独立内存空间)
                      ├── isolate B (用户 B 的堆 / 独立内存空间)
                      └── isolate C (用户 C 的堆 / 独立内存空间)
```

Cloudflare Workers 完全隐藏了 OS 进程层，将 **V8 isolate 单体** 作为执行的基本单位。在宿主机的单个进程内，毫无间隙地填充了数千个内存空间严格隔离的 isolate。

通过预先剥夺对文件系统访问或直接控制套接字等特权系统调用，从根本上消除了他人代码窥视同一宿主机内相邻内存区域的风险。

## 冷启动的物理极限

启动容器（如 Docker）必须经过一系列步骤：容器镜像的层级展开、Linux 命名空间（Namespace）的初始化、虚拟网络接口的配置以及客户机进程的启动。无论如何优化，都需要数百毫秒到数秒的时间。

相比之下，isolate 的启动仅需“初始化 V8 堆区域”和“加载预编译的字节码”即可完成。由于不存在网络或虚拟机的启动序列，在物理限制下，可以在 1 〜 5 毫秒内开始处理请求。

## 架构选择边界

| 处理性质                               | 最佳选择                  | 依据                                      |
| -------------------------------------- | ------------------------- | ----------------------------------------- |
| Web API、轻量级业务逻辑、数据中继      | **V8 isolate（Workers）** | 启动在毫秒量级，空闲成本为零              |
| 长时间运行的批处理、FFmpeg、Playwright | **Cloudflare Containers** | 必须具备完整的 Linux 内核和二进制执行环境 |
| 等待外部连接（DB 查询、外部 REST API） | **V8 isolate（Workers）** | 因 CPU 时间计费，网络等待时间免费         |
| 对单一资源的串行化与互斥控制           | **Durable Objects**       | 将请求聚合至全球唯一的实例                |

在引入适用于 Node.js 的库时，可以使用 `nodejs_compat` 兼容性标志，但这仅能提供 `Buffer`、`crypto`、`events` 等接近 Web 标准的部分抽象层。以 `fs` 进行本地磁盘操作为前提的设计，与 isolate 的理念根本不兼容。
