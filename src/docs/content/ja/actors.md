# Durable Objects と Actor モデル

Durable Objects（DO）は「状態を持つ小さなサーバー」と紹介されることが多い。しかしその本質は、並行コンピューティングの古典的理論である **Actor モデル（アクターモデル）** の純粋な実装である。この背景を理解すると、なぜ DO がオブジェクト指向のクラス構文で定義され、なぜメソッド呼び出しが 1 つずつ直列化されるのかという必然性が腑に落ちる。

## Actor モデルが課す 4 つの規約

Erlang のプロセスや Akka の Actor に代表される Actor モデルは、分散環境で安全に状態を保つために次の規約を定める。

1. **唯一無二の同一性（Identity）**: すべてのアクターは一意な識別名（ID または名前）で指し示される。同一の名前を指定する限り、物理的に同一の実体に到達する。
2. **私有された状態（Private State）**: 状態はアクターの内部にのみ閉じており、外部のプロセスから直接メモリを覗き見ることはできない。
3. **メッセージ通信（Message Passing）**: アクター間のあらゆるやり取りは、非同期メッセージの送受信によってのみ行われる。届いたメッセージは受信トレイへ順に積まれる。
4. **一度に一つだけの処理（Turn-based Processing）**: アクターは受信トレイからメッセージを 1 件ずつ取り出し、順番に処理する。内部で同時に複数の処理が走らないため、競合状態（Race Condition）が発生し得ない。

共有メモリの排他制御や分散ロックの複雑さに悩まされることなく、状態の物理的な配置場所（ロケーション透過性）をプラットフォームに任せられるのが最大の利点である。

## Durable Objects と Actor の対応関係

| Actor モデルの概念   | Cloudflare Durable Objects の実装                                   |
| -------------------- | ------------------------------------------------------------------- |
| アクターの識別名     | `env.ROOM.idFromName('room-1')` で生成される一意の ID               |
| 私有された状態       | `this.ctx.storage`（内蔵 SQLite）および `this` のインスタンス変数   |
| メッセージ           | クラスに定義された型付き RPC メソッド、または `fetch()`             |
| 受信箱と直列化       | インフラ層が完全保証。メソッド呼び出しは 1 件ずつ直列に実行         |
| アクターの消滅と復活 | メモリ不足時の退避（Hibernation）と、次期リクエスト到着時の即時復元 |
| 物理的な配置位置     | 原則として、その実体に最初にリクエストを送ったエッジ（Colo）近傍    |

## なぜ関数ではなくクラスで書くのか

クラス構文が強制される理由は、**クラスこそが「振る舞いの定義単位」であり、同時に「デプロイとスキーマ移行の最小単位」だからである**。

同一の振る舞いを持つアクターの実体を、部屋名やユーザー名ごとに何万個と生成する。この要件を満たすには、振る舞いを表す「型（クラス）」と、個々の状態を保持する「インスタンス（名前）」を明確に切り分けなければならない。

```ts
export class ChatRoom extends DurableObject {
  async join(user: string) {
    const members = (await this.ctx.storage.get<string[]>("members")) ?? [];
    if (!members.includes(user)) {
      members.push(user);
      await this.ctx.storage.put("members", members);
    }
    return members;
  }

  async alarm() {
    // 設定されたアラーム時刻に起床し、古いメッセージを一掃する
    await this.ctx.storage.deleteAll();
  }
}
```

RPC メソッド `join` に同時に複数のクライアントからアクセスが殺到しても、内部では 1 件ずつ確実に直列化して実行される。配列の読み出しと書き込みの隙間に別の処理が割り込んでデータが破損する心配はない。

## 考慮すべきスループットの境界線

- **単一インスタンスのスループットは 1 CPU コア相当に制限される**。何十万ものアクセスを 1 つの DO インスタンスに集中させれば当然ボトルネックになる。部屋ごと、テナントごと、ユーザーID ごとに細かくインスタンスを分割配置する設計が基本となる。
- **`await` で非同期処理を待機している合間には、別のメッセージの処理が差し込まれる可能性がある（Interleaving）**。状態の整合性を保つ際は、`await` を挟む前後で状態の不変条件が崩れていないかを意識する必要がある。
- アイドル状態のインスタンスは自動的にハイバネーションへ移行し、CPU 費用はゼロになる。常時接続の WebSocket を扱う際も、Hibernation API を利用すれば接続維持のための待機課金を発生させずに済む。
